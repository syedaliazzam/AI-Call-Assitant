# ADR-0072: Saving calls to Google Drive, and a "saved" email to the team

- **Status:** Accepted (developer, 11 Nov 2026: SQL approved; email over SMTP instead of Resend; notes only when Save transcript is off) · Web now; desktop 1.6.0 after the developer's browser checks.
- **Date:** 2026-11-11
- **Architecture reference:** `docs/architecture/kite-architecture-v3.1.md` §3.3, §5 (Settings), §7.1–7.4, §8.1, §10.1
- **Supersedes / superseded by:** amends ADR-0068 decision 1 ("recordings are never uploaded"): a recording is now uploaded **when the person connects their own Google Drive and leaves "Save calls to Google Drive" on**. Builds on ADR-0049 (encryption pattern) and ADR-0050 (one production database, additive migrations).

## Context

The team wants each call's recording, transcript and notes in a shared Google Drive folder after the call, and a short email to the team saying it is there. Constraints from the brief:

- Scope `https://www.googleapis.com/auth/drive.file` only (never `drive`, `drive.readonly`, Calendar or Gmail).
- The Google project is the developer's own test project today (External, testing mode: refresh tokens expire after 7 days) and will be swapped for the team's by changing only environment values.
- Live calls keep the whole computer: nothing uploads during a call.
- Recordings live only in the desktop shell's Recordings folder (ADR-0068); Vercel functions cannot carry large bodies (4.5 MB).
- No tokens, file names, addresses, transcript text or ids in logs. Email never carries call content.

## Decision

1. **Connect (server).** `GET /api/google/connect` starts OAuth with `drive.file`, `access_type=offline`, `prompt=consent`, `include_granted_scopes=false`, PKCE (S256), and a **state signed** with a key derived from `BETTER_AUTH_SECRET` (HKDF label `kite-google-oauth-state-v1`) that names the signed-in account, a nonce and a 10-minute expiry. The nonce and PKCE verifier sit in an httpOnly, SameSite=Lax cookie on `/api/google`. `GET /api/google/callback` accepts only its own state, for the same account, with the cookie (CSRF), exchanges the code and requires `drive.file` and a refresh token. The redirect URI is the address the person is on when it is a trusted Kite address (the custom domain or the vercel.app address), else `BETTER_AUTH_URL`.
2. **Tokens.** The refresh token is stored only encrypted, in a new table `google_drive` (AES-256-GCM with `KITE_DATA_KEY_V<n>`, bound to the account, the ADR-0049 pattern), never sent to a page or logged. `GET /api/google/access-token` (signed in, 30 a minute per account per server instance) refreshes and caches an access token in the instance's memory until five minutes before it expires. A refresh refused with `invalid_grant`, `invalid_client`, `unauthorized_client` or any other 4xx marks the connection **reconnect**; queued uploads wait and continue after the person reconnects (which keeps the folder and settings).
3. **Folder.** Google Picker (folders only; My Drive and Shared Drives; `setSelectFolderEnabled(true)`; `setAppId(NEXT_PUBLIC_GOOGLE_APP_ID)`) picks the folder; `POST /api/google/folder` reads it from Drive (`supportsAllDrives`) and stores Drive's own id, name and Shared Drive id. `GET /api/google/picker-config` gives the Picker key and project number to signed-in people only. Nothing (client id, folder, account) is hard-coded.
4. **Settings → Google Drive.** Connected · folder ↗ · Change folder · Disconnect (revokes at Google, then deletes the row; the row goes even when Google cannot be reached, and the page says so) · "Save calls to Google Drive" (on after connecting) · Reconnect when needed · the email switch, "Also notify" (≤ 20 valid addresses) and the last 20 notifications with Retry, or "Email not set up". In the **desktop app** Connect, Reconnect and Change folder open the web Settings in the **system browser** (the shell loads only the Kite address); the rest works in place, and the page reads the status again when its window comes back to the front.
5. **Folders and names.** In the chosen folder: `"<YYYY-MM-DD> <Company or title> – <Session title>"/Recordings` (`"<YYYY-MM-DD HH.mm> Part N.mkv"`, `"… Part N stereo.webm"`) and `/Transcripts` (`"… Transcript.txt"`, `"… Transcript.pdf"`, `"… Notes.pdf"`), local time, names cleaned of characters Windows, macOS or Drive refuse. Every folder and file Kite makes carries a private tag (`appProperties`, a SHA-256 hash of the session id, or of the session id and the file key; never the id itself). Before making a folder or uploading a file Kite looks for its tag, and keeps every Drive id it learns, so **nothing is made twice** — even after this device forgets its state. A different folder chosen later starts the session again in the new folder.
6. **The queue (device).** End queues the call (after its lines, notes and recording are saved) in a device-local Dexie store `driveUploads` (version 11; not synced) when the account saves to Drive (or, offline, did last time). A background uploader runs in one window of the profile at a time (Web Lock `kite.drive-uploader`): a few seconds after a page opens, when a call is queued or Drive settings change in any window, when the computer comes back online, and every minute. It never starts while the call lock is held, and stops between files and chunks when a call starts.
7. **Uploads.** Resumable uploads straight to Google (`supportsAllDrives=true`), in 8 MiB chunks (a multiple of 256 KiB); each file's upload address and progress are kept, and each resume first asks Google where it got to (`Content-Range: bytes */size`). A gone session (404/410) opens a new one (no file was made); a refused token gets a new one; a lost connection is retried after two minutes. **Recordings** are uploaded by the **desktop shell** (1.6.0) from its own Recordings index: the page sends the recording id, which file (main or stereo), the upload address and a short-lived token; the shell accepts only a UUID in its index and a `https://www.googleapis.com/upload/drive/v3/files?…upload_id=…` address, reads the file itself, uses Electron's `net.fetch` (the system proxy applies), and cuts off a chunk in flight the moment a call starts. **Transcripts and notes** are made by the page (the review download's text, for that call only; the notes PDF without the proposed lessons) and uploaded from the page — in a browser too. A session with "Save transcript" off saves no transcript (its notes are still saved). Local files are kept. Recordings exist only when the consent tick was given; the consent flow is unchanged.
8. **Saved.** When every file of a session is in, the page shows "Recording and transcript saved — <title>" with **Open in Drive ↗** (and the desktop app a native notification that opens the Drive link in the system browser; only a `https://drive.google.com` address is ever opened). Session cards and Meetings show "Waiting to upload to Drive", "Uploading to Drive 42%", "paused for the call", "Saved to Drive ↗", or the reason with Retry or Settings.
9. **Email (server).** `POST /api/drive/notify` takes only structured fields (session id, title, call start, length, ≤ 40 file names with their subfolder, a `drive.google.com` folder link, time zone, optional per-session "Also notify") — a body with any other field is refused, so an email cannot carry transcript, notes, answer or document text. The first request per (account, session) inserts a row in `drive_notification` (primary key: one email per session, ever); later ones send nothing. With SMTP configured and the switch on, one email goes to the person and the team list (the session's own list replaces Settings' when set; the session wizard has the field). It is sent over **SMTP with nodemailer** (10.2.1, MIT-0, no dependencies): port 465 with TLS from the start, any other port with STARTTLS required, 10-second connect, greeting and socket timeouts, nodemailer's logging off; each attempt has a fixed, hashed Message-ID. A failure is sorted by its code only (refused: authentication, sender or a 5xx reply; unreachable: anything else). The email's content is stored encrypted for Retry. Until `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` and `NOTIFY_FROM_EMAIL` are all set the email is inert ("not-set-up"), with no errors. **Send test email** (`POST /api/drive/test-email`) sends to the signed-in person only, 3 in 10 minutes per account.
10. **Schema.** Migration `0003_drive_connection.sql`, additive only: tables `google_drive` and `drive_notification`, one index. Applied with `pnpm --filter web db:migrate --prod` after the developer reads it (ADR-0050).

### Amendment, 11 Nov 2026 (before the desktop 1.6.0 release; developer's brief)

11. **One complete email per session.** A device no longer "notifies once"; it **reports** what it saved (each file's name, subfolder, stable key, Drive id, kind and part) when its uploads finish, and again when files were saved before an error. The server merges every report for the session into its `drive_notification` record (by file key and recording id, compare-and-swap on the ciphertext, since the Neon HTTP driver has no transactions). Each report lists the recording parts the account knows were made **during the calls it covers** (this computer's index and the synced recording records), so a browser's transcript and the desktop app's recording end up in one email. The record is `collecting` until every expected part and its stereo file are in Drive, then taken by one request for its one email (an update only one request can win). If the recording has not arrived **24 hours** after the first report, the email goes with what is there and says **"Recording upload pending"**; the 24-hour check runs when any of the person's devices asks for status or the notification list, and once a day in a Vercel cron (`/api/cron/drive-flush`, only with `CRON_SECRET`; inert without it). No schema change: `status` gains the value `collecting` and the encrypted content gains fields.
12. **The email.** Title, date, duration, an **Open folder in Drive** button, and a direct link per file: Recording Part N, Stereo audio, Transcript (PDF), Transcript (text), Notes (PDF). Plain text and simple HTML (no colours). Never transcript, notes, answer or document text. Recipients: the person, then the session's own list or the Settings list, worked out when it is sent.
13. **Older sessions are never emailed by themselves.** Jobs from before this change, and sessions uploaded with **Upload to Drive**, report with `manualOnly`; a new record for them is `not-set-up`, and Settings → Recent notifications offers **Send email** (with every file linked).
14. **Backfill.** With desktop 1.6.0, a finished session whose calls have a recording in this computer's index that is not in Drive (for example recorded on 1.5.2, whose shell could not upload) is queued again at the next run (the first launch) and only the missing files are uploaded. Sessions this device never saved show **Upload to Drive** on their card and in Meetings; their calls are worked out from what was kept (30-minute gaps; each call starts at the time its answers or notes recorded, so the notes PDF matches).

## Consequences

- Recordings, transcripts and notes can now leave the computer — **only** to the Drive folder the person picked, under the person's own Google account, and only after they connect. ADR-0068's "never uploaded" holds for everyone who does not connect.
- Kite's Google access is limited to the picked folder and the files Kite makes (drive.file); the Settings text says so.
- Desktop 1.5.x with the new web app uploads transcripts and notes but not recordings (the shell has no `driveUpload`); 1.6.0 uploads recordings of calls ended after it is installed.
- While the Google project is in testing mode, connections expire after 7 days; uploads then wait for Reconnect. Publishing the team's project removes that.
- Rate limits and the access-token cache are per server instance (Vercel may run several): the real ceiling is a few times 30 a minute — enough to stop a stuck page, not a hard quota.
- Upload state is per device: a session's progress shows on the device that saves it; "Saved to Drive" and the notification list come from the account and show everywhere.
- Each person reconnects after a project switch and picks the team folder (a token of one OAuth client does not work with another).

## Alternatives considered

- **Uploading through Vercel:** 4.5 MB request limit, double bandwidth, and recording bytes on Kite's servers. Rejected: the page and the shell upload straight to Google.
- **The shell holding the refresh token and orchestrating uploads:** business logic in the shell (CLAUDE.md forbids it) and a long-lived secret on the laptop. Rejected: the shell gets a short-lived token per file and does bytes only.
- **Broader scopes** (`drive`) to list the team folder freely: refused by the brief and unnecessary with tags.
- **Server-side record of every Drive file id:** cross-device but more stored data; the tags give the same "never twice" guarantee from any device.
- **Gmail API for the email:** a Gmail scope is forbidden.
- **Resend (an email API)** was the first choice (developer, 11 Nov 2026: replaced): a new third-party service and DNS records on the domain. SMTP with a company mailbox uses the mail system the company already has; no Resend code or dependency remains.
- **Uploading during calls at low priority:** measured headroom on the i5 laptop is small with recording on (ADR-0068, ADR-0069); waiting costs only minutes.
